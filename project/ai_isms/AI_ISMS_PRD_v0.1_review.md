# AI_ISMS_PRD v0.1 검토 보고서

- 검토일: 2026-06-11
- 검토 대상: `AI_ISMS_PRD_v0.1.md`
- 결과 반영본: `AI_ISMS_PRD_v0.2.md`

## 총평

전체 구조(기준-증적-미흡사항-개선계획-보고서의 연결, RAG 필수·Human-in-the-loop·감사 가능성 원칙)는 잘 잡혀 있다. 다만 **문서 내부의 범위 모순 1건**, **구현 단계에서 반드시 부딪히는 기술적 미정의 사항(권한 필터링, PII-임베딩 충돌, 신뢰도 산정, 색인 동기화)**, **측정 불가능한 성공 지표**가 발견되어 v0.2에 수정 반영했다.

---

## 1. 심각도 높음 (v0.2 반영 완료)

### 1.1 MVP 범위(5.1)와 릴리즈 계획(15.1)의 모순
- **문제**: 5.1 MVP 범위에는 "기본 취약점 진단 연동"과 "위험도 산정"이 포함되어 있으나, 15장 릴리즈 계획에서는 취약점 연동이 Phase 2, 위험관리가 Phase 3이다. 같은 문서 안에서 MVP 정의가 두 가지로 읽힌다. 16장 리스크에서 스스로 "범위 과대"를 지적하면서도 MVP에 13개 기능 영역을 담은 것 자체가 그 리스크의 실현이다.
- **수정**: MVP에서 취약점 연동·위험평가를 제외하고 15장과 일치시켰다. 미흡사항의 위험도 필드만 MVP에서 수동 입력으로 제공하도록 절충했다.

### 1.2 점검 상태 모델에 평가값과 결재상태 혼재 (7.4)
- **문제**: "충족/부분충족/미흡/해당없음/판단불가"(점검 결과)와 "검토중/승인완료"(결재 상태)가 하나의 상태 목록에 섞여 있다. 이대로 구현하면 "미흡이면서 승인완료"인 항목을 표현할 수 없고, 통계·대시보드 집계가 왜곡된다.
- **수정**: **점검 결과**와 **워크플로우 상태**를 별개 필드로 분리했다(용어 정의에도 명시).

### 1.3 RAG 권한 필터링 방식 미정의 (6.5)
- **문제**: "권한 없는 문서는 검색 결과에 포함되면 안 된다"는 원칙만 있고 방식이 없다. 사후 필터(검색 후 제거)로 구현하면 top-k 결과가 비어 답변 품질이 흔들리고, 필터 누락 시 권한 우회 사고로 직결된다. 이 제품에서 가장 치명적인 보안 결함 지점이다.
- **수정**: 사전 필터(pre-filter) 적용, 색인 메타데이터에 권한 포함 및 권한 변경 시 동기화, 프롬프트 컨텍스트 한정, retrieval_logs 기반 사후 검증을 명시했다.

### 1.4 개인정보 마스킹과 RAG 색인의 충돌 (8.4 vs 7.6/9.1)
- **문제**: "민감정보는 마스킹되어야 한다"고 했으나, 증적 원문이 그대로 청크·임베딩으로 들어가면 화면 마스킹은 의미가 없다. AI 답변이 마스킹을 우회하는 경로가 된다. v0.1의 RAG 파이프라인 17단계에는 PII 처리 단계가 아예 없다.
- **수정**: 파이프라인에 **색인 전 개인정보·민감정보 탐지 및 마스킹** 단계를 추가했다(마스킹 전 원문은 암호화 저장소에만 보관).

### 1.5 간접 프롬프트 인젝션 (8.4)
- **문제**: "프롬프트 인젝션 방어"가 한 줄뿐이다. 이 시스템은 외부에서 업로드된 문서(증적, 진단 보고서, 외부자 계약서 등)를 LLM 컨텍스트에 넣는 구조라서, 문서 본문에 심긴 지시문에 의한 **간접 인젝션**이 1차 위협이다.
- **수정**: 간접 인젝션을 명시하고 시스템 지시/검색 컨텍스트의 구조적 분리, 의심 패턴 차단·로깅을 요구사항화했다. 16장 리스크 표에도 추가했다.

### 1.6 AI 신뢰도 산정 방법 미정의 (9.3)
- **문제**: 산정 요소 7가지만 나열되고 산정 방법·등급 체계가 없다. 특히 LLM에게 신뢰도를 자가 보고시키면 그 값 자체가 환각일 수 있어 "신뢰도 표시" 요구사항이 무력화된다.
- **수정**: LLM 자가 보고 금지, 검색 점수+메타데이터 기반 규칙 산정, 높음/중간/낮음 3단계, 낮음 응답의 판단불가 자동 전환 임계값 정책을 명시했다.

### 1.7 RAG 품질 평가 체계 부재
- **문제**: "근거 포함률 100%" 같은 지표는 측정 체계 없이는 검증 불가. 임베딩 모델·청크 전략·프롬프트를 바꿀 때마다 품질이 흔들려도 감지할 수단이 없다.
- **수정**: 9.5절 신설 — golden dataset, 검색/응답 품질 정기 측정, 변경 시 회귀 평가, 판단불가 과소·과대 판정 표본 검토, 피드백 환류.

## 2. 심각도 중간 (v0.2 반영 완료)

### 2.1 증적 생애주기와 벡터 색인의 동기화 미정의 (7.5)
- 증적이 만료·반려·교체되어도 기존 임베딩이 검색에 남으면 "만료 문서 제외" 요구사항과 모순된다. 또한 **승인 전 증적이 RAG에 반영되는지**가 모호했다. → 승인 증적만 기본 반영(정책 설정 가능), 상태 변경 시 색인 무효화를 명시하고 리스크 표에 "색인 동기화 누락"을 추가했다.

### 2.2 임베딩 모델 교체 가능성(8.2) vs 데이터 모델 누락 (10.1)
- 모델을 교체하면 기존 임베딩 전체가 무효가 되는데 임베딩 모델 버전 관리가 없었다. → `embedding_models` 테이블, 메타데이터에 모델명·버전, 재색인·병행 운영 요구를 추가했다.

### 2.3 데이터 모델 누락 테이블 (10.1)
- 7.3에서 "기준 간 매핑"을 요구하면서 매핑 테이블이 없고, 취약점-통제항목·자산-통제항목 연결 테이블도 없었다. → `control_mappings`, `vulnerability_control_links`, `asset_control_links` 추가. `evidence_files`와 `documents`의 관계(원본 vs 색인 사본)도 핵심 관계에 명시했다.

### 2.4 용어 정의 부재
- "미흡사항"과 "결함"이 혼용되고(7.8), 증적과 지식베이스 문서의 구분이 모호했다. → 1.1 용어 정의 표 신설.

### 2.5 판단불가 응답의 UX 미정의 (7.7)
- RAG 필수 + 보수적 응답 정책의 부작용은 "판단불가 남발"이며, 이는 제품 효용을 직접 깎는다. v0.1에는 판단불가 이후의 사용자 행동이 정의되어 있지 않았다. → 부족 증적 명시, 필요 증적 목록 원클릭 추가, 보완 요청 알림, 사유 코드화를 추가하고 리스크 표에도 반영했다.

### 2.6 성공 지표의 기준선(baseline) 부재 (13장)
- "50% 단축"은 도입 전 측정값이 없으면 산출 불가. → 파일럿 측정 기반 기준선 확보 방법을 명시하고, 품질 지표에 측정 수단(ai_citation_logs, 권한 우회 테스트, 9.5 평가)을 연결했다.

### 2.7 AI 로그 자체의 민감성 (7.18)
- 감사로그에 프롬프트·참조 청크 원문을 남기면 **로그 저장소가 제2의 민감정보 저장소**가 되는데 로그 접근통제 요구가 없었다. → AI 로그에 기밀등급·접근통제 적용, 위변조 방지 방식(해시체인/WORM) 구체화.

## 4. v0.2에 반영하지 않은 권고 (후속 버전 과제)

1. **요구사항 식별자 체계**: 기능 요구사항에 FR-XXX / NFR-XXX ID가 없어 기능명세서·테스트케이스와의 추적성이 없다. v0.3 기능명세서 작성 시 ID 부여를 권장한다. (지금 부여하면 v0.2 diff가 과도해져 보류)
2. **기준 버전 명시**: "ISO27001"이 2013판인지 2022판(Annex A 93개 통제)인지 명시 필요. ISMS-P도 고시 개정 버전 기준을 정해야 기준 매핑 작업량을 산정할 수 있다.
3. **취약점-통제항목 "자동 매핑"의 정확도 기준**: CVE→ISMS 항목 매핑은 자산 유형·취약점 분류 기반 룰셋이 필요하며, "자동"의 범위(전자동 vs 추천+승인)와 오매핑 허용 기준을 Phase 2 설계에서 정의해야 한다. 권장: AI 추천 + 담당자 확정(Human-in-the-loop 원칙과 일치).
4. **외부 LLM 전송 데이터 통제의 구체화**: "전송 데이터 통제 가능"(8.4)을 데이터 분류 등급별 허용 매트릭스(예: 기밀등급 상 증적은 외부 LLM 전송 금지)로 구체화 필요.
5. **19장 프롬프트의 위치**: "Claude 입력용 요약 프롬프트"는 제품 요구사항이 아니므로 PRD 본문보다 별도 부록 파일로 분리하는 편이 깔끔하다.
